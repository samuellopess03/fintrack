# SPEC-14 — Internacionalização e Localização (i18n / l10n)

## Contexto

O FinTrack é direcionado ao mercado brasileiro. Isso tem implicações
concretas em como dados são formatados, como datas são apresentadas,
como valores monetários são exibidos e como o sistema trata os formatos
de extrato dos bancos brasileiros. Este documento define os padrões de
localização aplicados em todo o sistema.

Internacionalização (i18n) é a estrutura que permite múltiplos idiomas.
Localização (l10n) é a adaptação para um locale específico. Na v1, o
sistema é localizado para `pt-BR` sem suporte a múltiplos idiomas —
mas construído de forma que adicionar outros locales no futuro seja viável.

---

## Locale padrão: `pt-BR`

Todas as formatações de dados usam o locale `pt-BR` como padrão:

| Dado              | Formato pt-BR              | Exemplo              |
|-------------------|----------------------------|----------------------|
| Moeda             | R$ símbolo antes, vírgula decimal | R$ 1.234,56   |
| Data longa        | DD/MM/AAAA                 | 15/05/2024           |
| Data curta        | DD/MM                      | 15/05                |
| Data relativa     | "hoje", "ontem", "há 3 dias" | Intl.RelativeTimeFormat |
| Número            | Ponto como separador de milhar, vírgula decimal | 1.234,56 |
| Percentual        | Vírgula decimal + %        | 12,5%                |

## Formatação de moeda

O Brasil usa o Real (BRL) com as seguintes convenções:
- Símbolo `R$` antes do valor, separado por espaço.
- Vírgula como separador decimal.
- Ponto como separador de milhar.
- Sempre duas casas decimais.

```typescript
// src/utils/currency.ts

const BRL_FORMATTER = new Intl.NumberFormat('pt-BR', {
  style:    'currency',
  currency: 'BRL',
  minimumFractionDigits: 2,
  maximumFractionDigits: 2,
})

// R$ 1.234,56
export function formatBRL(value: number): string {
  return BRL_FORMATTER.format(value)
}

// Para valores negativos (despesas no extrato): -R$ 150,00
export function formatBRLSigned(value: number, type: 'income' | 'expense'): string {
  const amount = type === 'expense' ? -Math.abs(value) : Math.abs(value)
  return BRL_FORMATTER.format(amount)
}

// Versão compacta para cards de resumo: R$ 1,2 mil / R$ 3,4 mi
const BRL_COMPACT_FORMATTER = new Intl.NumberFormat('pt-BR', {
  style:    'currency',
  currency: 'BRL',
  notation: 'compact',
  maximumFractionDigits: 1,
})

export function formatBRLCompact(value: number): string {
  if (Math.abs(value) < 1000) return formatBRL(value)
  return BRL_COMPACT_FORMATTER.format(value)
}
```

### Parsing de moeda (formulários)

O usuário digita `150,50` — o sistema precisa converter para `150.50` (float):

```typescript
// src/utils/currency.ts

export function parseBRLInput(input: string): number {
  // Remove R$, espaços e pontos de milhar; troca vírgula por ponto
  const normalized = input
    .replace(/R\$\s?/g, '')
    .replace(/\./g, '')      // remove separador de milhar
    .replace(',', '.')       // vírgula decimal → ponto
    .trim()

  const value = parseFloat(normalized)
  if (isNaN(value)) throw new Error('Valor monetário inválido')
  return value
}
```

### Armazenamento no banco

Valores são armazenados como `NUMERIC(12, 2)` no PostgreSQL — sem ponto
flutuante, sem risco de imprecisão binária. O Drizzle retorna como string
(`"150.50"`); a conversão para number ocorre na camada de service, não
no banco.

```typescript
// No service — converte string do banco para number
const amount = parseFloat(transaction.amount)
```

## Formatação de datas

```typescript
// src/utils/date.ts

// 15/05/2024
export function formatDate(date: Date | string): string {
  return new Intl.DateTimeFormat('pt-BR').format(new Date(date))
}

// maio de 2024
export function formatMonthYear(year: number, month: number): string {
  return new Intl.DateTimeFormat('pt-BR', {
    month: 'long',
    year:  'numeric',
  }).format(new Date(year, month - 1))
}

// "hoje", "ontem", "há 3 dias", "há 2 semanas"
const RELATIVE_FORMATTER = new Intl.RelativeTimeFormat('pt-BR', { numeric: 'auto' })

export function formatRelativeDate(date: Date | string): string {
  const diffMs   = new Date(date).getTime() - Date.now()
  const diffDays = Math.round(diffMs / (1000 * 60 * 60 * 24))

  if (Math.abs(diffDays) < 1)   return RELATIVE_FORMATTER.format(Math.round(diffMs / (1000 * 60 * 60)), 'hour')
  if (Math.abs(diffDays) < 7)   return RELATIVE_FORMATTER.format(diffDays, 'day')
  if (Math.abs(diffDays) < 30)  return RELATIVE_FORMATTER.format(Math.round(diffDays / 7), 'week')
  return formatDate(date)
}

// Input de data HTML usa formato ISO: YYYY-MM-DD
// Converter entre ISO (banco/API) e exibição (pt-BR)
export function isoToDisplay(iso: string): string {
  const [year, month, day] = iso.split('-')
  return `${day}/${month}/${year}`
}

export function displayToIso(display: string): string {
  const [day, month, year] = display.split('/')
  return `${year}-${month}-${day}`
}
```

## Parsing de extratos bancários brasileiros

Os bancos brasileiros têm formatos CSV e OFX com particularidades de localização.

### Formatos CSV por banco

Cada banco usa um formato diferente — daí a necessidade do padrão Strategy.

```typescript
// Nubank — CSV com cabeçalho em inglês, vírgula como separador
// date,category,title,amount
// 2024-05-15,Transporte,Uber*TRIP,18.50

// Itaú — CSV sem cabeçalho, ponto-e-vírgula como separador
// 15/05/2024;UBER *TRIP;18,50

// Bradesco — CSV com BOM UTF-8, encoding Windows-1252
// DATA;HISTORICO;VALOR
// 15/05/2024;UBER *TRIP;18,50

// Banco do Brasil — CSV com encoding UTF-8, vírgula como separador
// Data,Histórico,Documento,Crédito,Débito,Saldo
// 15/05/2024,UBER *TRIP,,18,50,1000,00
```

O parser CSV deve detectar ou receber o banco de origem para aplicar as
regras corretas de parsing. Na v1, o usuário informa o banco ao fazer upload.

### Handling de encoding

Arquivos de bancos mais antigos usam Windows-1252 (Latin-1) em vez de UTF-8.
O parser converte antes de processar:

```typescript
import { decode } from 'iconv-lite'

async function readFileWithEncoding(filePath: string): Promise<string> {
  const buffer = await fs.readFile(filePath)

  // Detecta BOM UTF-8
  if (buffer[0] === 0xEF && buffer[1] === 0xBB && buffer[2] === 0xBF) {
    return buffer.slice(3).toString('utf-8')
  }

  // Tenta UTF-8 primeiro; se falhar, tenta Windows-1252
  try {
    const text = buffer.toString('utf-8')
    // Verifica se a decodificação faz sentido (sem caracteres de substituição)
    if (!text.includes('\uFFFD')) return text
  } catch {}

  return decode(buffer, 'win1252')
}
```

## Fuso horário

O Brasil tem múltiplos fusos horários (UTC-3, UTC-4, UTC-5). O FinTrack
adota as seguintes convenções:

### Armazenamento
- Timestamps (`created_at`, `updated_at`, `finished_at`) são armazenados
  como `TIMESTAMPTZ` (com fuso) em UTC.
- Datas de transação (`date`) são armazenadas como `DATE` (sem fuso) — o
  dia em que o usuário informou a transação, independente do fuso.

### Exibição
- Datas de transação são exibidas sem conversão de fuso (são apenas datas, sem hora).
- Timestamps de sistema (data de criação, data de importação) são exibidos
  no fuso local do browser: `new Intl.DateTimeFormat('pt-BR', { timeZone: Intl.DateTimeFormat().resolvedOptions().timeZone })`.

### API
- Timestamps são transmitidos como strings ISO 8601 com UTC: `2024-05-15T14:30:00Z`.
- Datas de transação como strings `YYYY-MM-DD`: `2024-05-15`.
- O frontend nunca envia datas com componente de hora para transações.

## Mensagens de erro em português

Mensagens de erro exibidas ao usuário são em português, mesmo que o
código interno use inglês. O Zod tem suporte a mensagens customizadas:

```typescript
// src/shared/validation/pt-br-messages.ts

export const ptBrMessages = {
  required:       'Campo obrigatório',
  min_length:     (n: number) => `Mínimo de ${n} caracteres`,
  max_length:     (n: number) => `Máximo de ${n} caracteres`,
  invalid_email:  'Email inválido',
  invalid_date:   'Data inválida',
  positive_number:'Valor deve ser maior que zero',
  invalid_uuid:   'Identificador inválido',
}

// Uso nos schemas
const CreateTransactionSchema = z.object({
  description: z.string()
    .min(1,   { message: ptBrMessages.required })
    .max(255, { message: ptBrMessages.max_length(255) }),
  amount: z.number()
    .positive({ message: ptBrMessages.positive_number }),
})
```

## Estrutura para i18n futuro

Embora a v1 suporte apenas `pt-BR`, a estrutura deve permitir adicionar
novos idiomas sem refatoração:

```
src/
└── i18n/
    ├── index.ts          ← configura o locale ativo
    └── locales/
        └── pt-BR/
            ├── common.json      ← termos globais (Salvar, Cancelar, Fechar)
            ├── transactions.json ← termos do módulo de transações
            ├── reports.json
            └── errors.json      ← mensagens de erro para o usuário
```

Na v2, integrar `react-i18next` para carregamento dinâmico de traduções
sem alterar componentes.
